# Go 编码风格规范

> 本文是对 Google Go Style 系列文档的中文归纳，不是逐字翻译。
> 内容以代码可读性和惯用写法为中心，不包含项目目录、数据库、安全、CI/CD 等工程流程规范。

## 1. 依据与规则层级

本文主要参考：

- [Go Style Guide](https://google.github.io/styleguide/go/guide)：规范性、权威性文档，优先级最高。
- [Go Style Decisions](https://google.github.io/styleguide/go/decisions)：规范性文档，对具体风格问题给出统一决策；与 Style Guide 冲突时以 Style Guide 为准。
- [Go Style Best Practices](https://google.github.io/styleguide/go/best-practices)：非强制的实践建议，用于说明常见场景下如何应用规范。
- [Go Style Overview](https://google.github.io/styleguide/go/)：说明各文档的定位与层级。
- [Effective Go](https://go.dev/doc/effective_go)：Google Go Style 所假定的社区共同基础。

本文使用以下措辞：

- **必须 / 禁止**：来自核心指南或明确的 Style Decision，应作为默认评审标准。
- **应该 / 不应该**：强烈推荐，偏离时应有清晰理由。
- **可以 / 建议**：依赖具体场景，以可读性为最终判断依据。

规范不能替代工程判断，也不应成为无意义的大规模格式改造理由。新增和修改代码应遵循最新约定，存量问题可在相关变更中逐步改善。

## 2. 核心原则

代码质量按以下顺序衡量：

1. **清晰（Clarity）**：读者能理解代码做什么，以及为什么这样做。
2. **简单（Simplicity）**：用满足行为和性能目标的最简单方式实现。
3. **简洁（Concision）**：保持高信噪比，使关键差异容易被发现。
4. **可维护（Maintainability）**：便于未来安全地修改和扩展。
5. **一致（Consistency）**：与包、项目和更广泛的 Go 代码保持一致。

这些原则存在冲突时，前者优先。例如，不能为了简洁牺牲清晰，也不能为了局部一致继续扩大一个已知的不良模式。

### 2.1 面向读者写代码

- 代码被阅读和修改的次数远多于首次编写，应优化阅读体验，而不是减少作者的输入量。
- 名称和代码结构应首先表达“做什么”；无法从代码本身看出的业务原因、语言陷阱和性能取舍，再由注释解释“为什么”。
- 避免聪明但陌生的技巧。复杂性确有必要时，应通过说明、测试和示例标出其原因与使用约束。
- 优先使用最小机制：语言内建结构优先于标准库，标准库优先于新增依赖或自建框架。

## 3. 格式与布局

### 3.1 自动格式化

- 所有 Go 源文件必须符合 `gofmt` 输出；建议用 `goimports` 同时整理导入。
- 不与格式化工具争论缩进、空格和括号样式。

### 3.2 行长度

- Go 代码没有固定的最大行宽。
- 行过长时，优先提取局部变量、辅助函数或选项结构，而不是按列数机械换行。
- 函数签名通常保持一行；函数调用也不应仅因行长随意拆分。
- 长字符串、URL 不应仅为满足行宽而拼接成多段。
- 必须换行时，按参数的语义分组，避免让续行与代码块缩进混淆。

### 3.3 控制流

- 先处理错误或终止条件，让正常路径保持左对齐。
- 终止分支之后不写多余的 `else`。
- 条件表达式中变量写在比较符左侧，不使用 Yoda 风格。
- `switch` 的 `case` 末尾不写多余的 `break`；需要跳出外层循环时使用带标签的 `break`。

```go
result, err := load()
if err != nil {
	return err
}
use(result)
```

## 4. 命名

### 4.1 通用规则

- 标识符使用 `MixedCaps` 或 `mixedCaps`，不使用 snake_case；常量也不使用 `MAX_VALUE` 或 `kMaxValue`。
- 下划线仅在少数情况使用：测试、基准和示例函数名，`*_test` 测试包，以及操作系统或 cgo 等底层互操作标识符。
- 名称长度与作用域大小成正比，与使用频率成反比。小作用域可以用短名称，大作用域需要更具体的名称。
- 名称描述值在当前上下文中的含义和用途，而不是值的来源或数据类型。
- 不在名称中重复包名、接收者类型、参数类型或上下文已经表达的信息。
- 不通过随意删字母制造缩写；使用社区熟悉且含义唯一的缩写。

```go
// Good
package yamlconfig

func Parse(input string) (*Config, error)

// Bad: 包名和返回类型已经提供了这些信息。
func ParseYAMLConfig(input string) (*YAMLConfig, error)
```

### 4.2 包名

- 包名简短、明确，只用小写字母和数字；多词包名保持连续小写，如 `tabwriter`、`oauth2`。
- 避免 `util`、`common`、`helper`、`model` 等缺乏领域含义的包名。
- 从调用点审视名称：`bytes.Buffer`、`http.Client` 本身应读起来清晰，不应形成重复表达。
- 包名不应容易被常见局部变量遮蔽。
- 除解决冲突或改善明显不清晰的第三方包名外，不重命名 import；同一个包在相邻代码中应使用相同别名。

### 4.3 缩略词

常见缩略词保持整体大小写一致：

- `URL` / `url`，不写 `Url`。
- `ID` / `id`，不写 `Id`。
- `DB` / `db`，不写 `Db`。
- 多个缩略词分别保持完整，如 `XMLAPI`、`xmlAPI`。
- `iOS`、`gRPC`、`DDoS` 等有约定写法的词，按其正常书写方式处理，并为导出性做必要调整。

### 4.4 函数、方法和变量

- 返回某个值的函数通常使用名词式名称，执行动作的函数通常使用动词式名称。
- 一般不使用 `Get` 前缀；远程调用或高成本计算可使用 `Fetch`、`Compute` 等词显式传达成本。
- 接收者名应是类型名的一到两个字母缩写，并在该类型所有方法中保持一致；不使用 `this`、`self` 或 `_`。
- 单字母变量只用于含义显然的短作用域，例如索引 `i`、坐标 `x`、Reader `r`、Writer `w`。
- 不在较大作用域中用局部变量遮蔽标准库或常用包名。
- 常量按角色命名，而不是按值命名；`const Twelve = 12` 通常没有意义。

## 5. 注释与文档

- 所有顶层导出名称必须有文档注释；行为或含义不直观的未导出声明也应该有注释。
- 文档注释是完整句子，通常以被描述的名称开头，并按正常句子使用标点。
- 注释优先解释原因、限制、边界条件和使用义务，不复述代码。
- 注释没有强制行宽；长段落宜在约 80 或 100 列附近自然换行，但 URL 等不应强拆。
- 每个包只能有一个包注释，紧邻 `package` 声明；长包文档可放在 `doc.go`。
- 包应尽量提供可运行的 `Example`；可运行示例放在测试文件中，并作为测试执行。
- 在开发和评审时预览 Godoc，确认段落、列表、代码块和链接渲染正确。

```go
// Encode writes the JSON representation of req to w.
func Encode(w io.Writer, req *Request) error { /* ... */ }
```

## 6. 导入

- import 默认不改名。发生冲突时，优先重命名更本地、更项目专属的包。
- 导入别名遵循包命名规则，不使用大写或下划线。
- Protocol Buffer 包通常使用含 `pb` 的别名，gRPC 生成包通常使用含 `grpc` 的别名。
- 导入按标准库、其他包、Proto 包、副作用导入分组；具体项目可交给 `goimports` 统一。
- 空白导入 `_` 只应出现在 `main` 包或确实依赖副作用的测试中；库包原则上禁止隐式引入副作用。
- 禁止点导入 `import .`，因为它隐藏了标识符来源。

## 7. 错误处理

### 7.1 返回和检查

- 用 `error` 表示函数可能失败，并将其作为最后一个返回值。
- 导出函数返回 `error` 接口，不返回具体错误指针类型。
- 每个错误必须被处理、返回或在极少数情况下明确忽略；忽略时说明为什么安全。
- 不使用 `-1`、空字符串等带内值表示失败。无法给出原因时可返回 `(value, ok)`，需要原因时返回 `(value, error)`。
- 调用方收到非 `nil` 错误后，除非 API 文档另有保证，不应依赖其他返回值。

### 7.2 错误文本和结构

- 错误字符串通常小写开头且不以标点结尾，因为它可能被上层继续组合。
- 面向人的完整日志、测试失败或 UI 文本可按正常句子书写。
- 调用方需要区分错误类别时，提供可编程检查的结构：哨兵错误、自定义错误类型或状态码；禁止解析错误文本。
- 使用 `errors.Is` 和 `errors.As` 检查被包装的错误。
- 添加错误上下文时只补充当前层独有的信息，不重复底层已经包含的路径、操作名等内容。
- 是否使用 `%w` 取决于是否承诺调用方可以观察底层错误；使用 `%v` 则只保留文本。错误链是 API 的一部分，应有意识地设计。

```go
f, err := os.Open(name)
if err != nil {
	return fmt.Errorf("load configuration: %w", err)
}
defer f.Close()
```

### 7.3 错误与日志

- 返回错误时通常不要在当前层再次记录，让最终处理者决定记录、重试、降级或忽略，避免重复日志。
- 日志应包含定位问题所需的上下文，但不得泄露个人或敏感信息。
- ERROR 级别应代表可采取行动的问题，不只是“比 WARNING 更严重”。

## 8. 语言与 API 设计

### 8.1 结构体、复合字面量和零值

- 项目手写代码禁止声明匿名结构体，所有结构体必须定义为有明确名称的类型。
- 禁止使用内联 `struct { ... }`、匿名嵌套结构体、`struct{}` 信号类型以及匿名结构体测试表；应提取为表达用途的命名类型。
- 每个结构体类型必须有中文注释，说明其职责和使用边界；导出结构体的注释必须同时符合 Go Doc 规则并以类型名开头。
- 每个结构体字段必须具有中文注释或有实际语义的 tag 标记。用于序列化、配置、校验或持久化的字段应使用 `json`、`yaml`、`validate`、`db` 等对应 tag。
- 不得添加无意义 tag 以规避字段注释要求；字段含义、默认值、单位、可选性或安全约束不直观时，即使已有 tag 也必须补充中文注释。
- 初始化其他包定义的结构体时必须写字段名，避免与字段顺序和新增字段耦合。
- 包内结构体也应在字段较多或显式名称更清楚时写字段名。
- 不影响理解时省略零值字段，使读者聚焦真正配置的内容。
- 多行字面量的闭合括号与起始位置保持相同缩进，并保留尾逗号。
- 空切片局部变量优先写 `var items []T`，不要让 API 区分 `nil` 切片和长度为零的非 `nil` 切片；判断为空使用 `len(items) == 0`。

### 8.2 函数和结果参数

- 项目手写代码禁止使用匿名函数和闭包，包括内联回调、`go func() { ... }`、`defer func() { ... }`、匿名 HTTP Handler 和匿名测试函数。
- 需要回调、并发任务、延迟清理或子测试时，必须提取为有明确名称的函数或方法；需要携带状态时，使用命名结构体及其方法。
- 禁止用立即执行匿名函数隐藏初始化、错误处理或控制流；应使用命名函数并显式返回结果和错误。
- 函数应保持单一职责和合理长度。函数超过一个正常阅读范围，或同时包含多个处理阶段、大量分支、深层嵌套及重复错误处理时，必须评估并优先拆分。
- 拆分后的函数必须具有明确名称、独立职责和清晰的输入输出；禁止只为减少行数而提取难以理解、无法复用或隐藏关键控制流的碎片函数。
- 确有必要保留较长函数时，必须保证主流程清晰，并使用中文注释说明不能合理拆分的原因和关键阶段。
- 参数很多时，先考虑拆分职责；仍然复杂时可使用选项结构体，让调用点自描述并允许后续扩展。
- `context.Context` 不放入选项结构体，始终显式作为第一个参数传入。
- 仅在多个同类型返回值需要区分、调用方对某结果负有特殊义务，或 `defer` 需要修改结果时命名返回值。
- 裸 `return` 只适合非常短且不会产生歧义的函数。
- 不为节省几个字节而传 `*string`、`*io.Reader` 等指向小值或接口的指针。
- 人类可读输出中的字符串可能为空或包含控制字符时，优先用 `%q` 而不是手工加引号。

### 8.3 值接收者与指针接收者

- 方法需要修改接收者、结构体不可安全复制或体积较大时，使用指针接收者。
- map、func、channel，以及无需修改的 slice 通常使用值接收者。
- 小型、不可变、自然表示“值”的类型通常使用值接收者。
- 同一类型的方法尽量统一使用指针或值接收者；不能确定时优先指针。
- 禁止复制包含 `sync.Mutex` 等不可复制字段的值。通常，如果 `T` 的方法主要定义在 `*T` 上，也不要复制 `T`。
- 性能选择应以真实基准测试为依据，不能压过正确性和可读性。

### 8.4 接口和泛型

- 没有真实需求时不要先创建接口；“service”“repository”等概念名称本身不构成接口需求。
- 接口应小而专注，由使用方根据实际需要定义；仅在包内使用时保持未导出。
- 通常接受接口、返回具体类型。仅在封装或模式确有需要时返回接口。
- 不要只为测试而给 RPC 客户端再包一层手写接口，也不要为测试在生产 API 中导出后门。
- 泛型用于解决已经存在的多类型需求，不用于预想中的复用，也不用于制造 DSL、断言框架或错误处理框架。
- 若只有一种实际类型，先写具体实现；若多个类型已有共同的有用行为，先考虑普通接口；大量 `any` 和类型分支才可能提示泛型更合适。
- 导出的泛型 API 必须充分文档化，建议提供可运行示例。

## 9. 并发、Context 与进程行为

### 9.1 Goroutine 生命周期

- 启动 goroutine 时必须让其退出条件清晰可见。
- 使用 context、WaitGroup、关闭信号等明确取消和等待机制，避免泄漏、数据竞争和不可预测的资源占用。
- 优先提供同步函数，让并发由调用方按需添加；同步 API 更容易理解、测试和组合。
- 并发任务需要统一取消和错误收集时，可以使用 `errgroup` 等合适的最小抽象。

### 9.2 Context

- `context.Context` 沿调用链显式传递，作为函数或方法的第一个参数。
- HTTP Handler、流式 RPC 等框架入口从请求或流中获取 context。
- 调用链中部通常不创建新的 `context.Background()`；优先继承调用方 context。
- context 用于跨边界传递截止时间、取消信号、追踪和请求级凭据，不用于普通可选参数。

### 9.3 Panic 和 Must 函数

- 禁止用 `panic` 处理正常错误，使用 `error` 和多返回值。
- `MustXxx` 仅用于启动或包初始化阶段的常量输入，以及便于构造测试值的测试辅助函数。
- 用户输入、请求处理和一般库函数不得使用 `MustXxx` 代替正常错误处理。
- 会直接终止进程的行为应限制在 `main` 或初始化边界，库代码不应替调用方决定退出进程。

## 10. 配置、全局状态与常用库

- 命令行 flag 只在 `main` 或等价入口定义；库通过 Go API、构造参数或结构体进行配置，导入库不得产生新增 flag 的副作用。
- 库不应强迫调用方使用全局可变状态。优先允许调用方创建互相隔离的实例。
- 全局状态只有在逻辑常量、对调用方表现为无状态且不会造成测试或调用顺序耦合等严格条件下才可接受。
- 若为便利提供默认全局实例，仍必须同时提供实例化 API；全局函数应只是实例 API 的薄代理，并明确并发与生命周期约束。
- 生成密钥、令牌等安全随机值必须使用 `crypto/rand`，禁止使用 `math/rand`。
- 无格式化需求时使用日志库的非格式化方法；避免无意义格式化。

## 11. 测试

### 11.1 测试框架和结构

- 使用标准库 `testing` 作为测试框架，不引入会遮蔽判断逻辑和失败上下文的断言 DSL。
- 表驱动测试必须定义命名用例类型，不得使用 `[]struct { ... }`；子测试回调必须使用命名函数或命名类型的方法。
- 子测试不是强制的；适合需要独立 setup/cleanup、过滤、并行控制或表驱动测试的场景。
- 子测试之间不得依赖执行顺序或共享的初始状态，并应能被单独运行。
- 表驱动测试只在多个场景具有相同测试逻辑时使用；若每行触发大量条件分支，应拆为独立测试或子测试。
- 测试辅助函数接收 `*testing.T` 时调用 `t.Helper()`；不得从测试启动的其他 goroutine 调用 `t.Fatal`。
- 测试可与被测代码使用同一个包；需要只验证公开 API、避免循环依赖或编写集成测试时，使用 `package foo_test`。

### 11.2 失败信息

测试失败信息应让维护者无需阅读测试源码也能定位问题，至少表达：

- 被测函数或操作；
- 关键输入或清晰的用例名称；
- 实际结果 `got`；
- 期望结果 `want`。

```go
if got, want := Normalize(input), "example"; got != want {
	t.Errorf("Normalize(%q) = %q, want %q", input, got, want)
}
```

- 输出顺序使用 got 在前、want 在后。
- 比较结构体、切片等复杂值时使用语义比较和清晰 diff，例如 `cmp.Equal` / `cmp.Diff`；比较 Proto 时使用适配选项。
- 不比较不稳定的序列化文本；先解析，再比较语义值。
- 只要后续检查仍有意义，使用 `t.Error` 继续收集失败；后续结果会失真或无法继续时才使用 `t.Fatal`。
- 测试错误语义时使用 `errors.Is`、`errors.As` 或明确的错误存在性布尔值，不解析错误字符串。
- 表格行必须有可读名称或在失败中打印输入，不使用行号作为唯一标识。

## 12. 局部一致性与未决事项

当规范没有明确意见时，应与相邻文件或同一包保持一致。但局部一致性不能成为下列行为的理由：

- 违反核心指南；
- 将已有偏差扩散到更多文件或公开 API；
- 引入真实缺陷；
- 延续固定行宽、断言库等已被明确否定的规则。

Google Go Style 对一些写法不作统一裁决，此时只需保持局部一致，例如：

- `var i int` 与 `i := 0`；
- `&T{}` 与 `new(T)`；
- 空 map 使用字面量还是 `make`；
- `cmp.Diff` 的 got/want 参数顺序，但失败信息必须写清 diff 图例；
- 无格式化内容时使用 `errors.New` 还是 `fmt.Errorf`。
