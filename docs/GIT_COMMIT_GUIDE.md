# Git 提交规范

> 本规范用于约束进入仓库永久历史的 Git 提交，包括本地提交、Pull Request 的 squash 提交和发布分支提交。
> 核心目标是让每个提交容易理解、评审、回滚，并能被自动化工具可靠解析。

## 1. 参考依据

本文主要参考：

- [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)：提交信息的结构和语义。
- [Git Commit Documentation](https://git-scm.com/docs/git-commit)：Git 提交、修订、签名和 trailer 的官方行为。
- [Google Engineering Practices：Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)：小而完整的变更原则。
- [Google Engineering Practices：Writing Good CL Descriptions](https://google.github.io/eng-practices/review/developer/cl-descriptions.html)：如何说明变更内容和原因。

本文在 Conventional Commits 允许自定义的部分做出项目级统一约定。

## 2. 核心原则

### 2.1 一个提交只做一件事

- 每个提交必须代表一个独立、完整且有明确目的的逻辑变更。
- 功能开发、缺陷修复、重构、格式化、依赖升级不应混在同一个提交中。
- 与变更直接相关的测试、文档和生成文件应与实现放在同一个提交中。
- 每个提交完成后，代码原则上都应能够构建并通过相关测试。
- 不按文件数量机械拆分。判断标准是能否用一句明确的话描述提交目的，以及能否独立回滚。

适合拆分的典型情况：

- 先补充现有行为的测试，再进行重构。
- 先做不改变行为的重命名或代码移动，再实现功能。
- 将依赖升级与使用新依赖能力的业务修改分开。
- 将大功能按可运行的垂直功能切片拆分。
- 将自动生成或机械格式化变更与人工逻辑修改分开。

### 2.2 提交历史面向未来读者

提交信息必须回答：

1. 改了什么？
2. 为什么要改？
3. 有哪些不能从代码差异直接看出的影响、限制或取舍？

禁止使用 `update`、`fix bug`、`changes`、`WIP` 等无法独立表达变更目的的永久提交信息。

## 3. Commit Message 格式

项目采用 Conventional Commits 结构：

```text
<type>[optional scope][!]: <description>

[optional body]

[optional footer(s)]
```

示例：

```text
fix(plugin): 达到线索目标后停止任务

收集到足够线索后，浏览器循环仍会继续执行，导致不必要的模型调用。
达到目标后不再调度新页面，但允许正在处理的页面正常结束。

Refs: #123
```

### 3.1 Header

Header 是提交历史列表中最常被阅读的内容，必须满足：

- 使用 `<type>: <description>` 或 `<type>(<scope>): <description>` 格式。
- `type` 和 `scope` 使用小写英文。
- 冒号后必须有一个空格。
- `description` 使用简体中文，优先采用“新增、修复、更新、移除、重构”等动宾结构描述本次提交完成的动作。
- 标题末尾不使用句号、感叹号等标点。
- 内容具体、可独立理解，避免只写实现手段或任务编号。
- 整行尽量控制在 50 个字符左右；清晰性优先，不为满足数字删除必要信息。
- 代码标识符、命令、协议名和无法准确翻译的技术术语保留原文，并使用反引号或通行写法。
- 提交信息统一使用 UTF-8 编码。

```text
# Good
feat(model): 记录每次模型请求和响应
fix(auth): 拒绝已过期的刷新令牌
docs(api): 补充分页限制说明

# Bad
更新代码
fix: 修复问题
feat: #123
fix(auth): 修复令牌问题。
```

### 3.2 Body

简单且含义明确的提交可以没有正文。存在以下情况时应该写正文：

- 修改原因无法从 diff 直接看出。
- 方案包含重要设计选择、兼容性考虑或已知限制。
- 缺陷只在特定条件下触发。
- 存在性能数据、迁移步骤或后续工作。

正文规则：

- Header 与正文之间必须空一行。
- 正文使用简体中文，专有名词、代码标识符和命令可保留英文。
- 重点解释背景和原因，避免逐行复述代码。
- 使用短段落，必要时使用列表。
- 记录足够的上下文，不应只依赖可能失效或无权限访问的外部链接。
- 行为经过评审发生变化后，提交前必须同步更新正文。

### 3.3 Footer

Footer 与正文之间空一行，用于表达机器可解析的元数据：

```text
Refs: #123
Closes: #456
Co-authored-by: Name <name@example.com>
Signed-off-by: Name <name@example.com>
BREAKING CHANGE: 刷新令牌改为一次性轮换策略
```

- `Refs` 用于关联事项，不表示自动关闭。
- `Closes` 仅在本提交确实完整解决事项时使用，并遵循代码托管平台语义。
- `Co-authored-by` 只用于真实共同作者。
- `Signed-off-by` 不是作者署名。只有项目要求 Developer Certificate of Origin 或同类声明时才使用 `git commit --signoff`。
- 不手工伪造作者、审核者、签署者或流水线生成的 trailer。

## 4. Type 约定

| Type | 用途 | 示例 |
| --- | --- | --- |
| `feat` | 新增对用户或调用方可见的能力 | `feat(plugin): 新增页面分析代理` |
| `fix` | 修复错误行为 | `fix(model): 保持工具调用顺序` |
| `refactor` | 不改变外部行为的代码重构 | `refactor(auth): 提取令牌校验逻辑` |
| `perf` | 可验证的性能优化 | `perf(store): 批量写入线索` |
| `test` | 只新增或调整测试 | `test(auth): 覆盖会话撤销场景` |
| `docs` | 只修改文档或注释 | `docs(api): 补充重试语义说明` |
| `style` | 只做格式、空白等无语义调整 | `style: 执行 gofmt 格式化` |
| `build` | 构建系统、依赖或打包配置 | `build: 升级 Go 工具链` |
| `ci` | CI 工作流和流水线配置 | `ci: 在拉取请求中运行竞态测试` |
| `chore` | 无法归入以上类别的维护工作 | `chore: 重置项目工作区` |
| `revert` | 撤销一个或多个既有提交 | `revert(plugin): 恢复顺序分析` |

选择规则：

- 新功能只能使用 `feat`，缺陷修复只能使用 `fix`。
- `refactor` 不得包含有意的功能变化；如果同时修复缺陷，应拆分或使用 `fix` 并在正文说明重构部分。
- `style` 不表示前端样式修改。CSS 或 UI 行为变化应根据语义使用 `feat` 或 `fix`。
- 谨慎使用 `chore`。能够准确归入其他类型时，不得用它回避分类。
- 一个提交同时符合多个类型，通常说明提交应该继续拆分；无法合理拆分时，以主要用户影响选择类型，并在正文解释。

## 5. Scope 约定

Scope 用于表示受影响的稳定模块或领域，例如：

```text
feat(plugin): 新增页面分析代理
fix(model): 保持工具调用顺序
docs(browser): 补充浏览器配对说明
```

- Scope 可选，但在仓库包含多个模块时应该使用。
- 使用稳定、简短、小写的名词；优先选择包、服务、组件或业务领域名称。
- 不使用文件名、开发者姓名、事项编号或临时分支名作为 scope。
- 同一模块必须保持相同写法，不随意创造近义 scope。
- 变更横跨多个模块且没有清晰主模块时，可以省略 scope；不要使用含糊的 `all`、`misc`。

## 6. 破坏性变更

任何不向后兼容的 API、配置、数据格式、命令行参数或行为变更，必须显式标记。

可以在 type/scope 后增加 `!`：

```text
feat(api)!: 强制使用游标分页
```

也可以在 Footer 中说明：

```text
feat(api): 强制使用游标分页

BREAKING CHANGE: 列表接口不再接受 page 和 page_size，客户端必须传入上一次响应返回的 cursor
```

项目要求：

- Header 使用 `!`，让历史浏览者能立即发现风险。
- Footer 同时写 `BREAKING CHANGE:`，明确旧行为、新行为和迁移方法。
- 破坏性变更可以属于任何 type，不只限于 `feat`。
- 不能只在 Pull Request 描述或发布说明中标记，提交本身必须携带该信息。

## 7. Revert 提交

- 已进入共享历史的错误变更优先使用新提交撤销，不改写远端历史。
- 使用 `git revert` 保留原变更和撤销关系；必要时编辑默认信息以符合本规范。
- Header 描述恢复的行为，正文记录被撤销提交的完整 SHA 和原因。
- 一次撤销多个提交时，正文列出所有 SHA，并说明它们为何必须一起撤销。

```text
revert(plugin): 恢复页面顺序分析

并发分析增加了生产环境中的模型超时。先撤销该变更，待重新设计并发限制后再恢复。

Reverts: 1234567890abcdef1234567890abcdef12345678
```

## 8. 提交前检查

### 8.1 检查提交内容

提交前必须确认暂存区只包含本提交相关内容：

```bash
git status --short
git diff --check
git diff --cached
```

- 使用 `git add -p` 按 hunk 暂存混合在同一文件中的不同逻辑变更。
- 检查新增、删除和重命名文件是否符合预期。
- 不得提交密钥、令牌、个人信息、生产数据或内部凭据。
- 不得提交调试日志、临时文件、编辑器配置和未约定的构建产物。
- 不得把用户或他人工作区中的无关改动顺手纳入提交。

### 8.2 验证代码

提交前必须执行与变更风险相匹配的检查：

- 格式化和静态检查。
- 受影响包的单元测试。
- 涉及公共接口或跨模块行为时的完整测试。
- 涉及并发时的竞态检测。
- 涉及生成代码时，确认重新生成后工作区无额外差异。

具体命令以仓库开发文档和 CI 配置为准。不得在明知检查失败时创建准备合并的提交。

### 8.3 检查提交信息

- Type 和 scope 是否准确？
- Header 是否能独立说明变更？
- 正文是否解释了必要的原因和取舍？
- 事项关联和共同作者是否准确？
- 是否存在需要声明的破坏性变更？
- 信息是否仍与最终 diff 一致？

## 9. Hook 与验证规则

- 本地 hook 用于尽早发现问题，CI 是最终质量门禁；两者不能替代人工检查。
- 原则上禁止使用 `git commit --no-verify` 绕过 `pre-commit` 或 `commit-msg` hook。
- 只有 hook 本身故障且变更紧急时才可临时绕过，并必须在评审中说明已手工完成的等价检查。
- 不得通过跳过测试、删除规则或伪造输出使提交通过验证。

## 10. 修改本地历史

### 10.1 尚未推送的提交

个人分支中尚未发布的提交可以整理：

- 使用 `git commit --amend` 修正最近提交的内容或信息。
- 使用 `git commit --fixup=<commit>` 和交互式 rebase 合并评审修正。
- 使用交互式 rebase 调整顺序、合并重复提交或修改信息。

整理后仍需重新检查最终 diff 和测试结果。

### 10.2 已推送或共享的提交

- 不得随意 amend、rebase 或强制推送已经被他人依赖的历史。
- 公共分支出现问题时，使用后续修复提交或 `git revert`。
- 确需重写个人远端分支时，先确认没有其他协作者依赖，并遵循仓库分支保护规则。
- 禁止对 `main`、发布分支或团队共享分支执行未经批准的强制推送。

## 11. Squash、Merge 与临时提交

- Pull Request 内可以存在便于评审迭代的 `fixup!` 临时提交，但进入主分支前必须整理。
- 使用 squash merge 时，最终 squash commit 必须符合本规范；不能直接采用无意义的 PR 标题。
- 使用 merge commit 时，功能提交本身仍应保持清晰；平台自动生成的 merge message 可作为例外。
- `WIP`、`fixup!`、`squash!` 等提交不得永久保留在主分支历史中。
- 自动生成的提交也应尽可能包含明确 type、scope、生成来源和影响范围。

## 12. 提交签名与身份

- Git 作者姓名和邮箱必须使用团队认可的真实身份，不使用共享身份。
- GPG/SSH commit signing 用于验证提交来源；`Signed-off-by` 用于声明贡献条款，两者含义不同。
- 仓库或组织要求签名时，所有进入受保护分支的提交都必须通过验证。
- 不修改或伪造他人的作者信息。代提交或共同开发时，使用正确的 author 和 `Co-authored-by` trailer。

## 13. 完整示例

### 新功能

```text
feat(plugin): 新增可配置的线索收集上限

允许每个任务定义目标线索数量。达到目标后停止调度新的浏览器页面，
同时保留已经收集的结果。

Refs: #184
```

### 缺陷修复

```text
fix(model): 重试时保留工具调用结果

重试时重新构建的消息列表没有包含已完成的工具调用结果，导致模型重复调用。
发生瞬时故障重试时，复用完整的会话状态。

Closes: #207
```

### 重构

```text
refactor(auth): 分离刷新令牌校验逻辑

将校验逻辑移入独立函数，不改变可接受的令牌或返回的错误，
为后续单独提交令牌轮换功能做好准备。
```

### 破坏性变更

```text
feat(api)!: 使用游标替代偏移量分页

游标分页可避免扫描期间插入新线索导致结果重复。

BREAKING CHANGE: 列表接口不再接受 page 和 page_size，客户端必须传入上一次响应返回的 cursor
```

## 14. 自检清单

- [ ] 提交只包含一个逻辑变更，可以独立理解和回滚。
- [ ] 相关实现、测试和文档保持同步，提交后代码可构建。
- [ ] 暂存区不含无关修改、敏感信息或临时文件。
- [ ] Header 符合 `<type>(<scope>): <description>` 格式。
- [ ] Type 和 scope 准确，description 使用简短、具体的中文动宾结构。
- [ ] 必要时正文解释了背景、原因、取舍和验证结果。
- [ ] Issue、共同作者、签署信息和破坏性变更声明准确。
- [ ] 已执行与变更风险相匹配的格式化、检查、测试和构建。
- [ ] 未无理由绕过 hook，未改写他人依赖的共享历史。
- [ ] 最终提交信息与实际 diff 一致。
